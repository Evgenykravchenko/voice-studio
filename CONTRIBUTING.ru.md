# Участие в проекте

[English](CONTRIBUTING.md) · **Русский** · [На главную](README.ru.md)

В Voice Studio можно помочь отчётами об ошибках, правками документации и небольшими
изменениями кода. Можно писать на русском и английском.

## С чего начать

| Задача | Куда обратиться |
| --- | --- |
| Разобраться с моделью или сценарием работы | [Discussions](https://github.com/Evgenykravchenko/voice-studio/discussions) и [руководство](docs/guide.ru.md). |
| Сообщить об ошибке | Найдите похожие [issues](https://github.com/Evgenykravchenko/voice-studio/issues), затем заполните форму ошибки. |
| Предложить функцию | Опишите свою задачу, текущую сложность и желаемый результат в форме предложения. |
| Сделать крупное изменение или перенос на другую ОС | Сначала обсудите подход и объём работы. |

## Как внести изменение

Создавать pull request могут только приглашённые участники. Остальные могут
открыть issue или обсуждение с предложением и ссылкой на свой fork. Сопровождающий
может перенести патч в ветку проверки, не выдавая права записи в репозиторий.

1. Если вы приглашённый участник, создайте отдельную ветку для одной задачи.
2. Пройдите [установку](docs/setup.ru.md) и прочитайте [инструкции разработчика](docs/development.ru.md).
3. Проверьте затронутые сценарии. Укажите команды или ручные проверки в pull request.
4. Если меняете описанное поведение, обновите русскую и английскую документацию.
5. В pull request опишите проблему, результат изменения и оставшиеся ограничения.

Изменения `main` и `release/*` проходят pull request и обязательные проверки.
Прямой push, force push и удаление этих веток запрещены. Доступен только squash merge;
название PR становится сообщением итогового коммита. При необходимости обновляйте
ветку через rebase. Перед слиянием завершите обсуждения проверки.

Владелец указан как code owner. Другим участникам требуется его одобрение.
Владелец может слить собственный PR без второго проверяющего, но отдельное правило
обязательного CI обойти не может. Успешные проверки не заменяют просмотр кода.

## Сообщения коммитов и названия PR

Используйте **`type(scope): description`** для каждого нового коммита и названия PR.
Контекст в скобках обязателен: одно слово из строчных латинских букв с возможными
цифрами, например `audio`, `voices`, `models`, `api`, `web`, `site`, `deps`, `ci`,
`repo` или `release`. Описание должно быть коротким и конкретным; для публичной
истории предпочтителен английский.

```text
feat(voices): add voice preview
fix(audio): correct playback volume
docs(setup): explain the first launch
chore(deps): update dependencies
```

| Тип | Для чего |
| --- | --- |
| `feat`, `fix` | Новая функция или исправление ошибки. |
| `docs`, `style` | Документация или форматирование без изменения поведения. |
| `refactor`, `perf` | Перестройка кода или производительность. |
| `test`, `build`, `ci` | Тесты, сборка или CI. |
| `chore`, `revert` | Обслуживание или осознанный откат изменения. |

Для несовместимого изменения допустим `!`: `feat(api)!: change the export format`.
Объясните его в теле сообщения. CI проверяет каждый коммит, добавленный PR,
и его название. Существующая публичная история сохраняется. Сообщения локальных
коммитов можно исправить до открытия PR. См. [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/).

## Выпуски и безопасность

Версионные теги, поддерживаемые ветки и порядок выпуска описаны в
[правилах релизов](docs/releasing.ru.md). Приватные сообщения об уязвимостях
описаны в [политике безопасности](SECURITY.ru.md). Веса моделей и личные записи
не должны попадать в файлы релиза.

Сейчас установка и запуск моделей поддерживают macOS 14+ на Apple Silicon.
Для Windows и Linux нужны подходящие движки и реальные проверки на этих системах.
До этого не обозначайте их как поддерживаемые. См. [планы](docs/roadmap.ru.md).

## Какие примеры можно публиковать

Используйте обезличенные тексты и синтетические аудио или записи с согласием
говорящего. Перед отправкой проверьте diff: записи, профили голосов, базы, веса,
локальные пути, токены и журналы с личной информацией не должны попасть в репозиторий.
Зависимости и кэши храните внутри проекта. Сохраняйте уведомления о лицензиях сторонних компонентов.

При изменениях моделей укажите языки, режимы голоса, окружение и лицензию модели.
Проверьте реальную обработку, помимо успешного скачивания файлов.
