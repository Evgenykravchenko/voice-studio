# Выпуски и правила репозитория

[English](releasing.md) · **Русский** · [Участие в проекте](../CONTRIBUTING.ru.md)

## Обычный порядок

Рабочая ветка → pull request → просмотр и успешные проверки → squash merge в `main`
→ версионный тег → GitHub Release. PR могут создавать приглашённые участники.
Остальные могут предложить изменение через issue или обсуждение со ссылкой на fork.

`main` служит основной веткой разработки. Ветка `release/0.1` нужна только для
поддержки старой линии выпуска, с теми же требованиями PR и CI. Для обычных функций
не нужны постоянные дополнительные ветки. Версионные теги создают администраторы;
обычные участники этого делать не могут. Активные правила запрещают перемещение
и удаление версионных тегов. Их определения находятся в `.github/rulesets/`;
изменение JSON само по себе не меняет настройки GitHub.

Исключение для администраторов касается только отдельного правила одобрения,
причём через PR. Базовое правило всё равно требует PR и успешный CI. Так владелец
может работать один, сохраняя обязательные проверки.

Базовое правило также требует результаты CodeQL и блокирует новые проблемы
безопасности уровня medium и выше, а также ошибки анализа. У защиты GitHub с
default setup есть исключение для PR Dependabot; обычный CI и просмотр владельцем
для них сохраняются. Изменения зависимостей и окружений проверяйте вручную.

## Названия версий

Используйте `vMAJOR.MINOR.PATCH`, например `v0.1.0`, для обычного релиза.
Единственный суффикс для промежуточной сборки: `-snapshot`, например
`v0.1.1-snapshot`. Такие сборки отмечайте как prerelease; beta, alpha и RC не используем.
`v0.1.0` станет первым обычным релизом, без отметки prerelease.
Snapshot-теги тоже защищены: существующий тег нельзя переносить на другой коммит.
Версия Python-проекта задаёт базовое `X.Y.Z`; версии интерфейса, Java и Python lock
должны совпадать. Перед созданием тега выполните `.venv/bin/python scripts/check-version.py --tag v0.1.0`
проектным Python; CI проверяет согласованность в каждом PR.
Patch подходит для совместимых исправлений, minor для функций, major для
несовместимых изменений после 1.0. До 1.0 описывайте несовместимые изменения явно.

## Как выпустить версию

1. Внесите подготовку выпуска через PR с названием вроде `chore(release): prepare v0.1.0`.
2. Проверьте CI и результаты безопасности выбранного коммита `main`. Отдельно проверьте нужные реальные сценарии моделей на Mac с Apple Silicon; Linux CI не подтверждает работу macOS inference.
3. Откройте **Releases → Draft a new release**. Выберите проверенный коммит и создайте для него новый версионный тег.
4. Просмотрите описание: изменения, установку и обновление, поддерживаемую macOS и ограничения. Не смешивайте лицензии моделей с MIT приложения.
5. Добавьте нужные файлы распространения в черновик. Не загружайте модели, окружения, базы, образцы голоса и личные результаты озвучки.
6. Опубликуйте проверенный черновик. Неизменяемые релизы блокируют подмену опубликованных файлов и связанного тега. Исправления выпускайте новой версией.

Из веток участников релизы автоматически не публикуются. Выпуск исходников
сам по себе не означает наличие установщика или сертификацию для продакшена.

## Проверки и границы бесплатного использования

Обязательный CI проверяет коммиты и PR, состав отслеживаемых файлов, статический
сайт, тесты и сборку интерфейса, Java-тесты и лёгкие Python unit-тесты. Используются
стандартные GitHub-hosted runners `ubuntu-24.04`. MLX и веса моделей не скачиваются.
CI не загружает кэши и артефакты сборки. Workflow Pages хранит небольшой проверенный
артефакт сайта один день.

Правила веток и тегов, приватные отчёты, CodeQL публичного репозитория,
предупреждения Dependabot и стандартные публичные runners сейчас доступны
без покупки плана или дополнения безопасности GitHub. Будущие условия сервиса
проект не контролирует. Большие runners, платные Marketplace actions, вычисления
приватных репозиториев, превышение хранения артефактов/Packages и другие платные
расходы аккаунта не входят в этот процесс. Не включайте их при такой настройке.

Для жёсткого ограничения оплаты владелец должен проверить **Settings → Billing
and licensing → Budgets and alerts**, поставить соответствующие бюджеты платного
использования в **$0** и включить **Stop usage when budget limit is reached**,
где это доступно. Настройки репозитория не доказывают состояние способов оплаты
и общих бюджетов аккаунта. См. [оплату Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
и [контроль бюджетов](https://docs.github.com/en/billing/how-tos/set-up-budgets).

Приватные сообщения описаны в [политике безопасности](../SECURITY.ru.md).
Состояние предупреждений и реальные правила доступны в GitHub. Зелёная проверка
не гарантирует безопасность любого кода или результата модели.
